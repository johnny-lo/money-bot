一、測試缺口（按風險排序）

原則：愈常改、愈核心、壞掉愈難發現的，愈優先補。純函式模組（links / extract / regions / report_helpers / ingest）覆蓋已經很好，缺的集中在「有 DB / 有狀態」的那層。

優先目標缺什麼建議做法
P1 core.py（788 行，0 測試） 記帳文字解析（handle_record_text 的 regex、多行記帳）、全部 CRUD handler、指令路由 process_text_message 這是最常被改到的檔案。先測純解析（不碰 DB 的部分），DB 部分用 FakeSession（仿 tests/test_recipe_repo.py 的模式）。補完才能安全地把 core.py 的 55 處 SessionLocal 轉成 session_scope（這次刻意沒動就是因為沒保護網）
P1 routes/record.py、routes/report.py API 整合測試：建立/修改/刪除、月份彙總、token 驗證 401 FastAPI TestClient + SQLite in-memory（override get_db dependency——這次改成依賴注入後，這件事變得很容易，這是 Depends(get_db) 最大的紅利）
P2 auth.py token 生成/驗證/30 分鐘過期/清理 純 dict 操作，monkeypatch datetime 即可，半小時的事
P2 recurring.py 每日固定收支：day_of_month 命中邏輯、active=0 不寫入 FakeSession + 指定日期參數化測試。它每天自動寫帳，錯了會默默寫錯一個月
P3 discordbot/ingest_handlers.py reply 補件流程、批次/單筆分流、多連結平行 拆成 package 後可單獨 import 了；用 fake message 物件測分流決策（不用真的連 Discord）
P3 einvoice.py 整合面 登入失敗、CAPTCHA 重試、多載具其中一組壞掉 已有 modal/翻頁的 fixture 回歸測試；登入流程要 mock Playwright，成本高，排最後

二、功能建議（從你們倆共用清單的情境出發）

推薦先做工作量：小/美食補強 slash 指令

food.enrich.backfill_all() 寫好了、今天也加上了 API 預算（預設 200 次封頂），但目前只能 docker exec 跑。加一個 /美食補強 指令（defer → 跑 → 回統計 embed：「補了推薦菜 12 家、照片 9 家、用了 87 次 API」），女友也能自己觸發。
為什麼：功能已經存在，差最後一哩的入口。idempotent + 預算保護都齊了，掛上去沒風險。

推薦先做工作量：小PWA 殼：manifest + service worker + icon

目前 frontend/ 沒有 manifest、沒有 service worker、沒有 icon——「加到主畫面」還不能用。vite-plugin-pwa 一個套件搞定：manifest（name/start_url=/m//theme #E67E22）、離線 fallback、192/512 icon + iOS 180 apple-touch-icon。
為什麼：這是「像個 app」的分水嶺。學習價值也高——SW 的 cache 策略是前端必修課。

第二批工作量：小照片來源標示

FoodPhoto.source（app/bot/google）已經存在 DB，但 /api/food/places 回的 photos 只有 URL 陣列。改回 [{url, source}]，前端顯示「📸 自己拍的 / 🤖 bot 收的 / 🔍 Google 的」。
為什麼：「去過」的店配自己拍的食物照，才是兩個人的記錄；Google 圖只是補位。後端一行、前端一個 badge。

第二批工作量：中PWA 長效 device token

現在 /m/?token=... 30 分鐘過期——PWA 釘在主畫面後，每次打開都要回 Discord 重拿連結，會把人逼瘋。建議：報表連結維持短效；PWA 另發長效 device token（首次用短效連結開啟時換發、存 localStorage、可撤銷）。
為什麼：這是 PWA 能不能日常用的關鍵。順便是一堂「session vs token、短效 vs 長效」的認證設計課。

第二批工作量：中地圖 InfoWindow / 詳情面板帶照片與推薦菜

enrich 補出來的 recommended_items 和照片，目前清單 API 有帶，但地圖點 pin 的資訊卡還沒呈現。詳情面板排版：✅ 必點（Google 評論萃取）→ ⚠️ 雷點 → 🏆 你們的評分 → 💬 心得 → 照片橫滑。
為什麼：選店當下「點開就知道要點什麼、避什麼」，這是這個模組的核心體驗。

有空再說工作量：中資料庫自動備份

現在 .backups/ 是手動 HTML dump。建議：cron 每天 pg_dump → gzip → 留 14 天，丟到 NAS 或雲端硬碟。帳務 + 兩年美食記錄是不可重建資料。
為什麼：postgres volume 一壞就全沒。一個 systemd timer + 10 行 script 的保險。

有空再說工作量：小照片上限與孤兒清理

單張照片大小上限（如 5MB）、每店張數上限（如 10 張）；另外寫個 cleanup_orphan_photos()：掃 media/ 裡 DB 沒記錄的檔案（FK 反向的洞今天已用 CASCADE+刪檔補上，剩「檔案在、列不在」的歷史殘留）。
為什麼：防磁碟被塞爆，順手收乾淨歷史垃圾。

三、建議的順序

  • PWA 開發路上順手做：manifest/SW → 照片來源標示 → 詳情面板 → device token（都在你既定的「地圖→消費→食譜」路線圖裡）
  • 回後端時：/美食補強 指令（30 分鐘）→ core.py 測試（這是解鎖 core 重構的前置）
  • 某個週末：pg_dump 備份 timer

附註：core.py 拆分與 session_scope 全面轉換，刻意排在「core 有測試之後」——對沒有保護網的核心檔案做大型重構，是回歸風險最高的事。
