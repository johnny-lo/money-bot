#🔀-資料流

文字指令 LINE 與 Discord 共用同一顆 core

訊息→ line_handler / commands.py→ core.process_text_message()→ 正則指令表（說明/分類/報表/固定/查詢/刪改/抓發票）→ fallback：「品名 金額」記帳→ DB 寫入→ 木須評論（Gemini）→ 回覆

雙介面約定：LINE 走 handle_*() 回 list[str]；Discord 走 *_data() 回 dict 給 embed builder。 同功能兩個出口，改邏輯只改中間。

拍照記帳 兩平台共用

圖片 bytes→ gemini_image() 回 JSON 品項陣列→ 正數 → transactions 負數（折扣）→ incomes→ 小計/折扣/實付回覆＋木須評論

電子發票補拓 einvoice.py ＋ invoice_backfill.py（真序列，故編號）

  1. 觸發：排程或手動呼叫 sync_with_backfill()，讀 invoice_sync_state 高水位（單列 id=1；首次 bootstrap = 昨天）。
  2. 算缺口：last_covered+1 ~ today，超過 60 天的部分跳過（平台多半也查不到）。
  3. 拆計畫：build_month_plan() 把缺口拆成逐月查詢（政府站限制每次查詢須同月）——前月整月查、當月以天數回推。
  4. 逐載具×逐月爬：_scrape_carrier() Playwright 登入 → CAPTCHA 交 Gemini 辨識（5 位數字，最多重試 4 次）→ vue-datepicker 設單月 → 每筆發票點開 Bootstrap modal 抓品項明細（嚴禁 go_back，會把 SPA 清單帶走）→ a.page-link「下一頁」翻頁（作用中頁碼沒前進即停，硬上限 60 頁）。
  5. 入庫：_save_invoices() 以 invoice_no 去重；逐品項各寫一筆 transaction，抓不到明細退化成「賣方＋總額」一筆；純代號品名加賣方前綴。
  6. 推進或凍結：全部載具全部月成功 → 高水位推進到 today；任一失敗 → 不推進＋發失敗卡，下次自動重抓整段（去重保證重抓安全）。
  7. 通知：#🧾-發票通知 摘要 embed＋「新增明細」第二張 embed；開機 catch-up 版 0 新增不發卡。

美食連結 ingest 三層抽取，逐層降級

#美食輸入 訊息→ links.detect_links()（平台判斷）→ L1 extract.from_url：yt-dlp 主力 ／ og fetch（facebookexternalhit UA）／ gmaps 解 URL→ L2 codex from_text 抽 {店名, 地區, 推薦菜, 類型}→ L3 deep_extract_via_codex（看圖＋搜尋，僅店名抽不到才動用）→ Places searchText 正名→ upsert（place_id 去重）→ 雷點摘要 best-effort→ embed 卡

抽不到店名 → ⚠️ 補件卡寫進 food.pending（in-memory），使用者 reply 卡片補店名即接回原流程。 多連結用 asyncio.gather + to_thread 平行，一連結一卡。 批次（≥2 行）另走：剝 - [ ] 勾選框帶出想去/去過 → 一次 codex 批解析 → semaphore 6 平行正名 → place_id 程序內去重（狀態只升不降）→ ✅高信心/⚠️需確認/❌找不到 總結卡，cap 60 行。

食譜與影片 ingest 複用同一條抽取基建

#🍳-食譜 連結→ food.extract.from_url（複用）→ codex 抽乾淨菜名→ url UNIQUE 去重入庫→ 卡片（reply 可改名）
#📜-歷史教學 連結→ food.extract.from_url（複用）→ codex 判 topic＋tags（失敗不擋入庫）→ 入庫＋掛標籤→ 卡片（reply：#主題 +標籤 -標籤 改標題）

差異只在後段：食譜擋 gmaps 連結、菜名抽不到走 pending 補名；影片標題退 blob 第一行、卡片底部固定附回覆小抄。

週報／月報 discordbot/reports.py

週日 21:00 pipeline→ _query_period() 彙總（總額/分類/Top N/每日）→ report_helpers 純函式（對比/異常/sparkline/儲蓄率/預算）→ codex 木須評語（餵入已算好的數字）→ bridge.post_embeds_sync()→ #📊-報表查詢

排程跑在同步 thread，靠 asyncio.run_coroutine_threadsafe(coro, bot.loop) 投遞到 Discord event loop。 注意：_bot_instance 是 module 級狀態，notify_*() 必須在 bot 主進程內呼叫，docker compose exec 子進程呼叫會靜默失敗。 AI 評語失敗時欄位顯示錯誤訊息，embed 照樣推。

PWA frontend/dist 掛 /m/

Discord 連結 /m/?token=短效→ POST /api/device-token 換長效→ localStorage 存 X-Device-Token→ GET/POST/PUT/DELETE /api/*→ 四 tab：美食地圖／消費／食譜／歷史影片

API 設計偏「整份清單給前端、過濾與隨機在前端做」；新增（食譜/影片/美食連結）仍走 Discord，因為需要抽取 pipeline。

#🗄️-資料庫PostgreSQL 15 · 10 tables

Schema 演進：啟動時 Base.metadata.create_all＋main.py 手動檢查補欄位（transactions 的 category / invoice_no、food_photos 的 FK），沒有 Alembic。 三個 UNIQUE 去重鍵是整個系統冪等性的支點。

transactions — 支出
item · price · category?（AI 填）· invoice_no?（發票去重鍵，index） · created_at（發票用消費日回填）
incomes — 收入
item · amount · category? · created_at。拍照記帳的折扣以「折扣：品名」形式寫進來。
recurring_records — 固定收支
type（expense/income）· item · amount · category? · day_of_month（1–28）· active（軟刪除：取消＝設 0）
food_places — 美食地圖
place_id（UNIQUE，Google 正名去重） · name · address · lat/lng · country/city/district · cuisine_type · recommended_items · caution_summary · status（想去/去過）· my_rating（1–5）· my_note · source_url · discord_message_id（✅ reaction 回查）
food_photos — 店家照片
food_place_id（FK CASCADE）· path（media/ 相對路徑，檔案在檔案系統）· source（app/bot/google）
recipes — 食譜
name（codex 清洗，可改）· url（UNIQUE 去重鍵） · platform · discord_message_id（reply 改名回查）
history_videos — 教學影片
title · url（UNIQUE 去重鍵） · topic（單一書架，index）· channel? · platform · discord_message_id
video_tags — 影片標籤
video_id（FK CASCADE）· tag（字串直存，去正規化多對多：查＝WHERE tag=?）
device_tokens — PWA 裝置
token（UNIQUE）· label（userAgent 簡述）· last_used_at（看哪台還活著）。無期限，撤銷＝刪列。
invoice_sync_state — 高水位
單列表（id 恆為 1）· last_covered_date：發票已成功涵蓋到的最後一天，驅動整個補拓機制。

#🔐-認證與防禦

兩層 token

Bot 指令（報表/美食地圖）→ 短效 token（30 分鐘，in-memory dict）→ POST /api/device-token 換發→ 長效裝置 token（DB、無期限、記 last_used_at）→ 之後全走 X-Device-Token header

require_token 收 query token 或 header 擇一。關鍵設計：只有短效 token 能換發——換發權綁在「剛從 Discord 拿到連結」這件事上， 洩漏的裝置 token 無法自我繁殖；踢裝置＝刪那列。

防禦清單

  • SSRF 守門（food/extract.py _is_safe_fetch_url）：og fetch 與 full-access codex 的種子 URL 都只放行公網 http(s)，擋 file:// 、loopback、私網、link-local（169.254 metadata）。
  • 上傳限制：Content-Type 白名單（不信任檔名）、單張 5MB、每店 10 張。
  • Stored XSS：報表頁品名/分類經 esc() 才進 innerHTML（發票品名是外部輸入）。
  • 去重三鍵：invoice_no / place_id / url UNIQUE；SELECT→INSERT 撞 UNIQUE 時 rollback 後回查當「已存在」（併發安全）。
  • 限流與預算：批次正名 semaphore 6、發票翻頁上限 60、批次 60 行、enrich API 預算 200 次（超過即停，重跑自動接續）。
  • 網路面：app 與 ngrok inspector 只綁 127.0.0.1，db 只在 docker 內網；對外唯一入口是 ngrok tunnel。

#📐-設計慣例

  • 純函式核心、I/O 邊界分明：計算與解析（report_helpers、links、regions、map_data、recommend、reply 語法、各 parse_*_json）全是無副作用純函式，pytest 直接測；I/O 包在薄 wrapper（places.py、extract 的 fetch 函式、_scrape_one）留給 monkeypatch。
  • Orchestrator 模式：每個域一條 ingest.py 串「抽取 → 正名 → 入庫 → 事後加值」，回 (結果, 原因) tuple，呼叫端決定卡片或補件。
  • Repo 模式：SessionLocal try/finally、ORM 進 dict 出；FastAPI 路由另用 Depends(get_db)。
  • 雙介面 core：同一份業務邏輯，LINE 出字串、Discord 出結構化 dict；embeds.py 是純呈現層，不碰 DB。
  • Best-effort 事後加值：雷點摘要、enrich 補強都是「失敗不影響主流程」，且 idempotent 可重跑補漏。
  • 失敗顯性化：發票失敗發失敗卡、AI 評語失敗在欄位裡寫錯誤訊息照樣推卡——寧可吵，不沉默。
  • 去重換冪等：所有自動化都假設「會重跑」，靠 UNIQUE 鍵讓重跑無害；高水位只在全成功時推進。
  • 降級鏈：yt-dlp→og fetch→deep extract；明細抓不到退賣方總額；菜名抽不到退 blob 第一行；AI 失敗不擋入庫。
  • 可接受的簡陋：pending 補件與短效 token 都是 in-memory、重啟即失——明知且接受，換取零依賴。
  • sync↔async 橋：排程（同步 thread）→ bridge → bot event loop；async 路徑呼叫 blocking 函式一律 asyncio.to_thread 包。
