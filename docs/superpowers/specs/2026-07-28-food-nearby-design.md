# 美食「附近有什麼」設計 spec

- 日期：2026-07-28
- 分支：master
- 狀態：設計定稿，待寫實作計畫（writing-plans）

## 目的

現在的美食清單回答不了使用者真正的問題。他的決策流程是三步：

> **鎖定願意移動的範圍 → 決定想吃什麼料理 → 挑一家有興趣的店**

App 只做得到第三步（篩出店的清單）。第一步完全沒有；第二步雖然有 12 個大類 chip，
但按下去之前不知道有沒有東西，等於要用猜的。

## 為什麼這件事 Google Maps 做不了（本功能的存在理由）

Google Maps 回答的是「**X 在哪裡**」——你得先知道要吃什麼才問得出口。
它不回答「**這附近有哪些選擇**」，因為對它來說附近有幾千家，列出來沒有意義。

但對這份清單有意義，因為清單**已經被使用者和女友篩選過一輪**：

- Google Maps：這附近有 40 家日式 → 然後開始一家一家看評價、篩雷店
- 這份清單：這附近有 3 家日式，**而且都是當初主動想去的**

「有沒有興趣」這個最貴的判斷，在存進來的當下就做完了。所以這份清單能給出
Google Maps 給不了的東西：**一份已過濾、可窮舉的選項菜單**。

料理分類（2026-07-28 的前一輪）不是在重造 Google 的輪子，它是這個功能的地基——
沒有受控大類就無法回答「這附近有哪幾種料理」。

## 關鍵性質：零後端改動、零 API 成本

`/api/food/places` 已經回傳 `lat/lng`、`cuisine_major`、`cuisine_minor`、`district`。
定位、距離、分組全部在裝置上算 → 拉滑桿即時反應、離線可用、不打任何 API。

## 已定決策

### D1｜範圍用直線距離，不用真實車程
純前端計算，零成本、即時、離線可用。使用者選的是「我願意跑多遠」的**門檻**，
不是在規劃路線，所以誤差不重要。真實車程要打 Routes API，而起點是即時 GPS
→ 無法預存、每次拉滑桿都要重算全部 112 家，慢且要錢且斷網就死。

### D2｜五個離散檔位，車程標註用手工校準表（不是公式）
手機上拇指精度有限，離散檔位比連續滑桿好按。

| 直線距離 | 標註 | 校準依據 |
|---|---|---|
| 1 km | 約 5 分 | 含紅綠燈與停車 |
| 3 km | 約 10 分 | 中壢區內 |
| **5 km** | **約 15 分**（預設） | |
| 10 km | 約 20 分 | 中壢→桃園市區 |
| 30 km | 約 40 分 | 中壢→竹北約 30 分、→台北約 50 分，取中間 |

**為什麼不用公式**：短程走市區、長程走國道，均速差兩倍以上，線性公式套不住。
`km × 3` 會把 30 km 算成 90 分（實際約 40 分），使用者看到就永遠不會按那一檔，
等於白做。只有 5 個固定檔位，查表比公式誠實也準確。
副作用：`geo.js` 不需要 `driveMinutes()` 函式，分鐘數是常數表。

### D3｜當成美食頁的預設畫面，但絕不卡住
```
進頁面 → locating（最多 6 秒，沿用 FoodMap.locateMe 現有 timeout）
   ├─ 拿到座標 → 附近模式
   └─ 拒絕 / 逾時 / 不支援 → **自動**退回清單模式
                             頂端細 banner：「沒有定位權限，顯示全部店家 · 重試」
```
退回是自動的，不是彈窗擋路。使用者永遠看得到自己的清單。
這是選「預設畫面」而非「第三個檢視」的唯一代價，必須設計掉。

### D4｜磚塊顯示家數，未分類歸「其他」
只顯示範圍內**真的有店**的大類，依家數由多到少排。家數是關鍵資訊——
只有 1 家的日式跟有 6 家的日式，決策不一樣。

`cuisine_major` 為空的店（目前 8 家）歸到「其他」磚塊，不會憑空消失。

### D5｜地區篩選在附近模式隱藏
範圍已經由距離決定，縣市/行政區 select 再存在只會跟距離打架。
想去/去過 chips **保留**且照常作用（去過的店也可能想再吃）。

## 架構

| 檔案 | 職責 |
|---|---|
| `frontend/src/geo.js`（新） | 純函式：`haversineKm(a, b)`、`groupByMajor(places)` + `RANGES` 常數表 |
| `frontend/src/Nearby.jsx`（新） | 純呈現：收 places + 座標 + 範圍，畫滑桿與磚塊，回報選中的大類 |
| `frontend/src/Food.jsx` | 加座標/範圍/檢視三態 state、定位流程與退路 |
| `frontend/src/index.css` | 磚塊格線 + 滑桿樣式 |

`Nearby.jsx` 不自己抓資料、不自己定位 —— 定位在 `Food.jsx`（資料的唯一主人），
與現有 `FoodList`/`FoodMap` 的分工一致（純呈現元件收 props、把互動回報上來）。

檢視切換：右上角按鈕三態循環 📍附近 → ☰清單 → 🗺️地圖。
按鈕**顯示下一個模式的圖示**（沿用現況：清單模式時按鈕長 🗺️）。

## 互動細節

- 點磚塊 → 選中，下方列出那幾家（複用 `FoodList`）；再點一下取消回全部
- 範圍內 0 家 → 「5 公里內沒有店家」+ 一鍵跳下一檔
- 座標**不自動追蹤**（耗電且無對應需求）。範圍滑桿右側有「📍 重新定位」小按鈕，
  按了才重新取座標；定位失敗 banner 上的「重試」走同一條路徑

## 驗證

前端**沒有測試框架**（無 vitest/jest、零測試檔，已確認 `frontend/package.json`），
所以純函式無法單測。驗證靠：

1. Playwright 用 `setGeolocation` 灌中壢座標 + 給 `geolocation` 權限 → 截圖驗磚塊家數
2. **不給權限**再跑一次 → 驗是否乖乖退回清單而非卡住（D3 的核心風險）
3. 手機上使用者親眼確認（AGENTS.md §4：手機 CSS 沒有自動化測試）

若日後要為 `geo.js` 加單元測試，需先引入 JS 測試框架 —— 那是另一個獨立決定，不在本範圍。

## 範圍外

- **真實車程**（Routes API）：D1 已說明為何不做
- **即時追蹤定位**：一次定位就夠，持續追蹤耗電且沒有對應需求
- **「其他」那 8 家的自動分類**：先前討論過的半夜 Playwright 爬蟲已否決
  （為 8 家店維護會被 Google 改版打壞的 DOM 選擇器，投報比太差）。
  真正該補的是**手動修改分類的路徑**——美食模組目前完全沒有修改功能，
  唯一的更正手段是刪掉重加。那是獨立的一輪。
