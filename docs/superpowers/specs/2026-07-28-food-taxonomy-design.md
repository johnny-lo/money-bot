# 美食地圖「料理兩層分類 + 行政區細化」設計 spec

- 日期：2026-07-28
- 分支：master
- 狀態：設計定稿（brainstorming + 兩份 Plan agent 收斂），已寫實作計畫

## 目的

美食地圖現在的分類顆粒度太粗，兩個面向都不堪用：

**地區**：`city` 被 `canon()` 砍後綴 → 桃園市/新竹市/新竹縣全糊成「桃園」「新竹」，
**新竹市（11 筆）和新竹縣（10 筆）完全分不出來**，竹北/竹東根本無法辨識。
`district` 欄位存的是**里名**（興南里、普仁里，105/112 筆），毫無用處；只有 3 筆是真行政區、7 筆 NULL。
而且 `city` 目前有**三種格式並存**：`台北市`（全名）、`桃園`（去後綴）、`臺東`（去後綴且用臺）。

**料理**：`cuisine_type` 是 LLM 自由填的文字，112 筆裡 30 筆空白、82 筆散成 **49 種**不同寫法，
從「咖啡」到「費城起司牛肉三明治」到毫無資訊的「小館」「食堂」「餐廳」。
沒有受控詞彙表 ＝ 沒有可用的篩選軸。

**目標**：料理走兩層（12 個受控大類 + 自由細類），地區細到鄉鎮市區
（桃園市中壢區 / 新竹縣竹北市 / 新竹縣竹東鎮）。

## 範圍外（明確不做）

**開車時間分類不做**。使用者選定出發點是「要求來的即時 GPS 定位」→ 起點每次都不同，
車程無法預先算好存進 DB，只能在裝置端即時計算，屬於不同的資料生命週期，另案處理。

## 現有機制關鍵事實（設計所依據，已對正式 DB 實測）

- **`address`（Google `formattedAddress`，zh-TW）112 筆全有**，且含真正的行政區：
  `320台灣桃園市中壢區興南里永樂街97號` → **整批回填零 Google API 呼叫**。
- **光改 `parse_address_components` 的優先序救不回來**：同樣兩個縣市，Google 對 id 57 給「平鎮區」、
  對 id 36 給 NULL；對 id 83 給「北區」，對 id 89（竹東鎮）/103（竹北市）給 NULL。
  修完優先序仍會留下 7 筆 NULL，且**竹北市/竹東鎮 Google 從沒給過** → 地址文字 parser 是必要條件，不是捷徑。
- **地址文字本身是髒的**：`臺北市`×18 vs `台北市`×1、`桃园市`×2（簡體）、
  `中坜市`×1（**2014 升格前的舊名，今為中壢區**）、`平镇区`、郵遞區號 3/5/6 位、
  id 61 尾端有垃圾 `… 45號1樓 No`、**3 筆**英文倒序（id 17、31、78）。
- **`canon()` 是模糊比對鍵，不是儲存格式**：只被 `region_matches` → `food/recommend.py:12` →
  `/美食推薦` 消費。改它會直接弄死既有查詢。
- **寫入 `city`/`district`/`cuisine_*` 的只有三個地方**，且全部經過 `food/repo.py:29 upsert_place`
  （`discordbot/commands.py:180`、`food/ingest.py:47`、`food/ingest.py:275`）→ 有單一咽喉點可收斂。
- **`upsert_place` 目前無條件覆寫 country/city/district**（`food/repo.py:42-45`）→
  一次退化的 Places 回應（缺 addressComponents）就把好資料抹成空。既有的潛在資料流失 bug。
- **既有 bug：`/美食推薦 台東` 回空**。`canon("臺東")="臺東"`、`canon("台東")="台東"`，
  `regions.py:72` 的 `q==c or q in c or c in q` 全部 false。本次統一台-form 後順手修好。

## 已定決策

### D1｜`city` 不變式
一律 22 個台灣縣市**全名、台不用臺**（`桃園市`/`新竹縣`/`新竹市`/`台北市`/`台東縣`）。
國外城市維持現況開放詞彙。選台不選臺的理由：`_CITY_ALIAS`（`regions.py:4-12`）本來就把
臺中市→台中市，且已有 21 筆是 `台北市`；選臺要改動更多列且與既有別名表對打。

### D2｜不動 `canon()`
儲存格式改用新的 `normalize_city()`，`canon()` 保持原樣當模糊比對鍵。
已逐值驗證回填後 `/美食推薦` 全部照常：`canon("桃園市")→"桃園"`、
`canon("新竹市")=canon("新竹縣")→"新竹"`、`canon("台北市")→"台北市"`（別名命中）、`canon("台東縣")→"台東"`。
它是**靠 `_strip_suffix` 的巧合**成立的 → 補測試釘住，避免未來有人改 `canon` 時無聲弄壞。

### D3｜`district` 不變式
屬於該縣市的合法鄉鎮市區，或 NULL。**永不是里/村**。用封閉查表保證，不靠 regex 形狀猜。

### D4｜台灣地址以 `address` 文字為單一真相
`addressComponents` 只負責 `country` 與**國外地址**（日/韓路徑一字不動）。
台灣列先跑 `parse_tw_address(address)`，拿不到 city 才退回 components，拿不到 district 就 NULL
（里比 NULL 更糟）。地址文字與 components 衝突時，**地址文字贏**。

### D5｜料理三欄
新增 `cuisine_major`（大類，12 選 1）+ `cuisine_minor`（細類），
**`cuisine_type` 原封不動留著當原始稽核文字**。
好處：回填只寫新欄 → 零遷移風險、完全可逆（`SET cuisine_major=NULL, cuisine_minor=NULL`）、
規則改良後可整批重推；且**舊的 PWA 殼（service worker 快取）照常運作**，
不會因為 JSON key 改名而整排卡片副標空白。

### D6｜判不出就是空字串，不設「其他」桶
空欄誠實且可查（`WHERE cuisine_major IS NULL`）；「其他」會永久混淆
「真的其他」與「我們規則沒中」，之後再也分不開。UI 在**顯示層**渲染成「其他」。

### D7｜12 大類詞彙表只住在 `food/cuisine.py` 一個地方
**不寫進 `food/extract.py` 的四個 LLM prompt**——兩份詞彙表必然漂移，且幻覺值會直接進 DB。
prompt 繼續產自由文字 `cuisine_type`，大類一律由 `classify()` 推導；
規則改良 → 重跑回填就整批重新分類。防線三層：規則單一來源 → 別名折疊 → 
`normalize_major()` 在持久化邊界做詞彙表成員檢查（越界值結構性寫不進去）。

### 詞彙表（使用者定案）

**大類（12，順序即 UI chips 順序）**：
日式、韓式、中式、台式、東南亞、西式、火鍋、燒烤、早午餐、咖啡甜點、飲料冰品、酒吧餐酒館

**落類規則**：菜系國別優先於品類。
- 拉麵 → 日式 / 細類「拉麵」
- 日式燒肉 → 日式 / 細類「燒肉」（**不是**燒烤）
- 牛肉麵 → 台式 / 細類「牛肉麵」
- 法式甜點 → 咖啡甜點 / 細類「法式甜點」
- 印度咖哩 → 東南亞（12 類沒有南亞桶，塞最近的亞洲異國）
- 費城起司牛肉三明治 → 西式 / 細類「三明治」

**實作上這條規則 = 最左關鍵字命中者勝**（中文的國別修飾語必在名詞前），
在 112 筆真實資料上驗證 100% 成立，比「先掃國別表再掃品類表」的兩階段更簡單且更可預測。
反例證據：`肉球尼尼` 的推薦菜是 `起司牛排漢堡、番茄燉雞歐姆蛋、中式煎餅、魚漢堡`，
兩階段會把這家漢堡店誤判成**中式**；最左命中正確給西式。

## 架構

```
food/tw_divisions.py   純資料：22 縣市 + 368 鄉鎮市區 + 縣市別名 + 升格舊名別名
food/regions.py        純函式：normalize_city / normalize_district / parse_tw_address
                              / resolve_region（D4 優先序的唯一入口）
                              + region_matches 加 district 比對
food/cuisine.py        純函式：MAJORS / normalize_major / classify
food/repo.py           唯一寫入咽喉點：upsert_place 內做正規化 + 分類 + 非空守衛
food/backfill_food_taxonomy.py
                       純規劃器（可單測、不連 DB）+ 薄寫入器
                       dry_run 預設 / 備份 / 逐列 commit / 冪等 / verify_invariants
```

**行政區表獨立成 `tw_divisions.py`** 的理由：368 筆資料放進 `regions.py`
會淹掉它「純函式、無 I/O」的定位；分開後 regions 仍然只有邏輯。

### 地址 parser 演算法

1. 折字：既有 `_S2T`（簡→繁）+ **另一張** `臺→台` 表
   （方向相反，別跟 `_S2T` 混在一起，下一個讀的人會搞錯）。
2. **縣市**：在 `TW_CITIES ∪ CITY_ALIASES` 掃**最左出現**、同位取**最長**。
   用全名比對天然解掉 `新竹縣竹北市` 不含子字串 `新竹市`。
3. **行政區（正向）**：取縣市 token 之後的字串，對
   `TW_DISTRICTS[city] ∪ DISTRICT_ALIASES[city]` 做**錨定在 index 0 的最長前綴比對**。
4. **行政區（倒向）**：正向沒中才跑，取縣市之前的字串做最長後綴比對（英文倒序地址）。
5. **輸出查表的正規字串，不是比中的原文** → 簡體/臺/升格舊名的差異在此結構性消失。
6. 非台灣完全不進這條路徑。

**為什麼錨定比對打敗 regex**：`300台灣新竹市東區南市里勝利路131號` ——
錨定在 index 0 只會比中「東區」，永遠碰不到「南市」；
任何 `[區鄉鎮市]` 掃描式 regex 都會吃成「東區南市」（Plan agent 實測重現過）。
里名同形是這批資料的常態，不是特例：`中壢區中壢里`、`竹北市竹北里`、
`台北市中正區新營里`（新營區在台南）、`新竹市東區新莊里`（新莊區在新北）。

## 回填安全

112 筆 → **人工目視 diff 是這裡最強的控制**，報表要設計成「給人讀」而非「給人略過」：
依 `(old → new)` 分組，`桃園 → 桃園市 ×57` 只佔一行，3 筆倒序地址才會跳出來。

- `dry_run` **預設 True**。
- 第一次寫入前備份到 `.backups/food_taxonomy_pre_<YYYY-MM-DD-HHMM>.json`（沿用既有 `.backups/` 慣例）。
- **中止閘**：任何台灣列解不出 city → 除非 `force=True` 否則拒絕寫入（靜默半吊子解析才是會爛資料的失敗模式）。
- 逐列 try/except + **逐列 commit** → 第 57 列爆炸不影響前 56 列。
- **冪等**：目標欄位與現值相同就跳過 → **第二次跑必須印 `0 changed`，這是冪等的證明，是必做步驟不是選配**。
- `mode="missing"`（預設，只補空）vs `mode="rules"`（規則改良後整批重推，仍不用空覆寫非空）。

## 上線順序（每一步 app 都是活的）

**schema → 寫入路徑 → 回填 → 讀取端。**

先回填後改寫入 → 中間任何一次 Discord 匯入都會無聲地重新污染那一列；
先改讀取端後回填 → 使用者會看到混格式；
先改 prompt → 會生出第二份詞彙表然後漂移（D7）。

## 已知取捨

- `/美食推薦 新竹縣` 仍會撈到新竹市的店（兩者 `canon` 後都是「新竹」）。
  這是現有契約，用測試把它釘成**刻意行為**而非未爆彈；要精準就打「新竹市」（新規則 2 認全名）。
- 12 大類沒有南亞/中東/墨西哥的家。使用者已裁示印度咖哩落東南亞；其餘落 NULL（D6，可回復）。
- **國外店目前 0 筆**，國外分支是唯一沒有真實資料可驗的路徑 → 那條路徑一字不改，
  靠現有的 Tokyo 單元測試（`tests/test_food_regions.py:46-55`）守住。
